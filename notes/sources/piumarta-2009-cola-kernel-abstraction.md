# COLA Kernel Abstraction (Ian Piumarta, 2009-08-22, VPRI Memo M-2009-007)

Source: https://tinlizzie.org/VPRIPapers/m2009007_COLA_kern.pdf (9 pages; the figures did not
survive text conversion, and the code is reflowed).

## A. Classification

Practical: a short design memo with one worked example, at the boundary between language and
operating system.

## B. Unity

A "kernel" can be reduced to a tuple of an entry point and a parent kernel, bound to procedure
activations and scoped dynamically by the call graph. That makes recursive virtualisation (services,
isolation, pre-emption, even whole-language semantics) an ordinary language feature costing a few
lines of compiler support.

## C. Outline of major parts

1. **Introduction:** virtualisation for isolation, and for cheap, safe experiments with new
   semantics. Inspired by Fluke's nested virtual machines.
2. **Kernels.**
   - 2.1 Representation: entry point plus parent, with optional extra state like a Unix "u area".
   - 2.2 Pushing a new kernel onto the current context.
   - 2.3 Calling an entry point: it runs with the *parent* kernel active, like entering a system
     call.
3. **Example: pre-emptive multitasking.**
   - A `tick` instruction decrements a budget in each function prologue and before each backward
     branch, and enters the kernel when the budget is exhausted.
   - Two one-line additions to the compiler (`compile-body`, `while`).
4. **Other uses:** concurrency models behind one interface, synchronisation, memory management and
   zone isolation, self-configuring communication, kernels as containers for whole-language
   semantics.

Artifacts named: the "STEPS core programming language" and its compiler (an IR that is interpreted
or compiled to native code), with `define-instruction`, `compile-body`, `while` and `compile-tick`.
The code style matches the Coke/early Maru lineage.

## D. Author's central problems

1. What is the smallest notion of an OS kernel that still provides isolation and services?
2. How can it nest (recursive virtualisation) and compose with language semantics?
3. How little compiler support does a real feature such as pre-emption need under this model?

## E. Key terms

- **Kernel:** a collection of primitive behaviours plus their state. Minimally (entry point,
  parent kernel).
- **Context:** a procedure activation; each has an active kernel, inherited by callees.
- **Kernel stack / pushing a kernel:** associating a new kernel with the current context until it
  returns. Scope is dynamic, along the call graph.
- **Entry point call:** a procedure call whose callee runs under the caller's kernel's *parent*.
- **Budget / tick:** a counter decremented at progress points; reaching zero enters the kernel.
- **Behavioural dual of objects:** objects encapsulate state statically; kernels encapsulate
  behaviour dynamically.

## F. Main propositions and arguments

1. **Kernels can be minimal tuples** (§2.1). Reasoning: everything else a kernel needs (state,
   services) can hang off the entry point and an optional record.
2. **Binding kernels to activations gives dynamic scoping of services and privilege for free**
   (§2, §2.2–2.3). Normal calls inherit the kernel; returns restore it; entry calls step up to the
   parent. So nesting falls out of the ordinary call discipline.
3. **Pre-emption needs only an instruction and two lines of compiler** (§3).
   - A program can only make progress by calling procedures or branching backwards.
   - So charging the budget in prologues and at loop back-edges bounds the time between kernel
     entries.
   - `tick` either enters the kernel (leaving four stack items, cleaned by `drop 4`) or skips the
     `drop`.
4. **The same mechanism generalises** (§4), as asserted: concurrency, synchronisation, memory
   management and language semantics can each be a kernel, globally or locally scoped.

## G. Critique

- **The example is demonstrated; the generality is asserted.** Only pre-emption is worked through;
  §4 is a plan.
- **Incomplete.**
  - Cost (a decrement and test at every call and back-edge) isn't measured.
  - Interaction with native code generated by back ends (as opposed to the interpreted IR) isn't
    discussed.
  - "Strong isolation via kernels" (§4.1 in the contents) has no body in the text.
- **Uninformed in one respect:** the memo doesn't engage with existing work on safe points and
  yield points in VMs (e.g. JVM safepoints), which use the same "calls and back-edges" argument.
- **Agreement where it counts.** The progress argument (calls or backward branches) is correct, and
  the dynamic-scoping design is elegant and small.

## H. What of it?

- **A cheap pattern for later.** If the rebuild ever needs interrupts, time limits or isolation
  (for example, running untrusted JIT'd code, or the `check` harness's runaway tests), a
  `tick`-style safepoint in the IR's prologue and loop back-edge is a two-line addition to the
  backend, not a runtime subsystem.
- **It confirms the lineage.** The STEPS core language's compiler had an IR that could be
  interpreted *or* compiled to native code, with instructions defined by `define-instruction`.
  That's the shape `emit.l`/`ir.k` inherit.
- **It's peripheral to the bootstrap and line-budget questions.** No line counts, and nothing on
  self-hosting.
