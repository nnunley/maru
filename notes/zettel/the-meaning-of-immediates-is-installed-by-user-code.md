# Even the behaviour of nil and integers is installed by user-level code, not fixed in the runtime

The COLA runtime does not know what nil or an integer is. Its two special vtables start empty, and they are filled only when the compiled kernel library runs statements that make the `UndefinedObject` family the nil type and the `SmallInteger` family the tag type. Until those statements run, sending any message to nil or to an integer is a fatal error. The white paper states this as a design choice: the two vtables are not predefined, are initialised by user code during startup, and may be modified or exchanged with another vtable at any time.

This pushes the grounding of the object system lower than one would expect. The C layer supplies only the mechanism (where to look for a value's behaviour), and the language layer supplies the policy (what that behaviour is). It is the same move the object model makes for lookup, applied to immediates, and it creates an ordering dependency in the bootstrap: the kernel must install these vtables before any code that sends to nil or to a number. A Maru evaluator generated by its own compiler would have to reproduce that order, or decide that immediates are grounded in the runtime and record the decision.

Source: Piumarta 2005, COLA white paper §4.2 (primary, "not predefined and are initialised explicitly in user-level code during startup"); idst-20070918 `function/objects/Object.st:27-28`, `object/id/libid.c:402-410` and `:611`.
