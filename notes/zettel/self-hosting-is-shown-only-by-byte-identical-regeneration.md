# Self-hosting is shown only by a seed-built system regenerating itself byte for byte

A system claims to be self-hosting when it is written in the language it implements. That claim is only demonstrated when a build started from a foreign seed produces a system that, run on its own sources, regenerates exactly the same output. At that fixed point the seed carries no information the sources do not, and can be thrown away.

Piumarta used the same test in two generations. In the COLA bootstrap (2005), the Pepsi compiler written in Pepsi had to produce byte-identical output to the disposable C++ compiler before the C++ version was discarded. In the original Maru, a C evaluator runs `boot.l`, `emit.l` and `eval.l` to produce `eval.s`; once assembled, `eval` run on the same three files produces an identical `eval.s`, and the C compiler leaves the loop.

The converse is the useful critical tool: self-hosting claims made without the regeneration check are unverified. The STEPS proposal's "singularity", in which the bootstrap seed becomes irrelevant, and OMeta's partial self-implementation, whose code generator stays in the host, are both asserted without it.

For the Maru rebuild, "the evaluator is generated by `emit.l`" has a precise acceptance test: bootstrap from the C seed, rebuild with the result, and require identical output. That test can live in `make check`.

Source: Piumarta, Maru project page (piumarta.com/software/maru), section "The process" (primary); Piumarta 2005, *Accessible Language-Based Environments of Recursive Theories* (VPRI RN-2006-001-a), §6.1 phase 2; Kay et al. 2006, STEPS NSF proposal (VPRI RN-2006-002), p. 11 (the unverified case).
