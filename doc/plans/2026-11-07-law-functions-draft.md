# Functions in law files (draft for review)

**Status:** accepted 2026-11-07 with both case forms (`|`, preferred, and one equation per line), list domains, and named
lists shared by laws and schemas; specified in `draft-ndn-maru-laws-and-rules-00` ("Functions and list domains").
gc-model.g's and gc-real.g's meanings move into gc-model.law next, and hash-ops.g's into hash.law.

## The problem

A law file says how terms are generated, but not what a generated term means. In `check/laws/hash.law`, the rules make
terms such as `big(1)`, `half(3)` and `deep(2)`. What each one stands for lives elsewhere:
- `big(n)` is 2^53 + n, written in a grammar action in `check/hash-ops.g`;
- `half(n)` is n + 0.5, a Maru function in `check/laws/hash.l`;
- `deep(n)` is a nest of n + 6 pairs, also a Maru function in `check/laws/hash.l`.

So a reader of the law can't see what is being tested, and a change to a term's meaning lands in two or three files.
This is the case the memory note "claims in law files" warns about: extend the laws language, not support helpers. The
same holds in `gc-model.law`, whose operations' meanings are two grammars, `gc-model.g` and `gc-real.g`.

## The proposal

Two additions, both evaluated where claims are evaluated. Rules stay first-order, symbolic and untouched, so the engine,
its three modes and the mutants still see only first-order rules ([R-higher-order-expansion]).

1. **An anonymous function, KScript's form:** `(x, y) -> expression`. It may appear wherever a claim's expression may:
   - in a claim;
   - in a law's `let`;
   - in a file-level `let`;
   - in a `classify` condition.

   It closes over the law's bindings and the file's lets. It is applied as any function is, `f(a, b)`, so a `let`-bound
   function reads like a reference.

2. **A function by cases over terms:** one clause per term shape, each a pattern and a result, tried in order:

   ```
   let value = num(n) -> n
             | dbl(n) -> n * 1.0
             | big(n) -> 9007199254740992 + n
             | half(n) -> n + 0.5
             | pair(a, b) -> [value(a) | value(b)]
             | Nil -> []
   ```

   - A pattern is a term written as rules write them: a lower-case name binds, a capitalised one or a number matches
     itself.
   - The first clause whose pattern matches gives the result.
   - A term no clause matches is the error `E_NO_CASE value: big(x)`, naming the function and the term. It is never a
     quiet nil.
   - It may call itself, as `value` does for pairs. Terms are finite and generated by size, so the recursion ends.

   The cases compile to a tree grammar over the term, as the repo walks trees elsewhere. They are not a cond chain.

With both, `hash.law` says what it tests in one file. A reference then receives values, not terms:

```
law numbers: all a: numkey(a), b: numkey(b), k: kind(k). finds_iff_same(value(a), value(b), k) = accept by exhaustion
```

## Lists of values as domains

A third, smaller addition follows from the same question: binding a law's variable to the elements of a list.

```
law numbers: all a in [0, 2, -7, 9007199254740992 .. 9007199254740993], k: kind(k). ...
```

- This is exhaustion over constants, with no `fact` per value.
- Ranges already work inside lists (`range.law`).
- Today the same thing takes a schema and a relation: `for k in ...: fact numkey(k)`, plus `numkey(a)` in the law.

## Alternatives considered

- **Why not keep meanings in grammars and references (the status quo)?** The meaning sits apart from the law that tests
  it, and a reviewer has to read three files to know what `big(1)` is.
- **Why not compute in rules (`rule k_big: number(n) => key(9007199254740992 + n)`)?** Arithmetic in rules makes them
  more than first-order terms. Unification, enumeration by size and the mutants all assume symbolic terms; a computed
  value can't be unified back or mutated meaningfully.
- **Why not embed Maru (`let value = { (lambda (k) ...) }`)?** It would put a second language into law files and give
  them no law-level errors. A law file would no longer read without knowing Maru.
- **Why not `\x. e` or `fn x => e`?** KScript's `(x) -> e` is already the shared world's function syntax, so one form
  serves both. It needs `law.g` to try `(params) ->` as a function before `cexpr.g`'s member access `a->b`. The two
  overlap (`(n) -> n` is either one), so in a law file `->` is always a function; law files have no C structs to reach
  into.

## Open questions for you

1. **Syntax for cases.** `|`-separated clauses, as drafted, or one `let` per clause, `let value(num(n)) = n`, as
   equations?
2. **Lists as domains.** Is `all a in [...]` wanted now, or only the two function forms?
3. **gc-model.law.** Should its two grammars also move into the law file as functions by cases? They have side effects
   (writes, worlds, throws), so a by-cases function there would run effects. That is a larger step, and I'd do it after
   hash.law.

## What it would cost

- **law.g:** two rules (a function and a case list) and one domain form.
- **law-compile.l:** compiling a function to a Maru lambda, and the cases to a tree grammar.
- **Tests:**
  - `law_cexpr` reads each form;
  - `law_rules` fixtures for a function in a claim, a case function, `E_NO_CASE` and a list domain;
  - hash.law rewritten to use them, with `check/hash-ops.g`'s key rule and the `ops-*` makers gone.
